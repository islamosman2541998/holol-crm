# سجل مراجعة وإصلاح مشروع Holol CRM

آخر تحديث: 2026-09-16

## الهدف

هذا الملف هو المرجع الثابت لكل التعديلات الناتجة عن مراجعة المشروع. الأولوية هي حماية بيانات النظام العامل، وعدم كسر أي مسار قائم، وتنفيذ تغييرات قاعدة البيانات عبر migrations إضافية قابلة للتراجع فقط.

## قواعد التنفيذ والرفع

- لا يتم تعديل migration قديم تم تشغيله على السيرفر.
- لا يتم حذف أو إعادة إنشاء أي جدول أو بيانات حالية.
- تغييرات قاعدة البيانات الجديدة تكون إضافية، مع فحص مسبق للتعارضات.
- لا يتم تشغيل اختبارات تستخدم `RefreshDatabase` على قاعدة البيانات الفعلية؛ الاختبارات تعمل على SQLite معزولة.
- تظل التعديلات الحالية غير المرتبطة بالمراجعة محفوظة، ومنها `public/build.zip`.
- قبل الرفع: نسخة احتياطية لقاعدة البيانات والملفات، ثم وضع الصيانة لفترة قصيرة أثناء `migrate` وتهيئة الكاش.
- بعد الرفع: فحص الدخول، الصلاحيات، إنشاء عرض سعر، تحويله لمبيعة، تسجيل دفعة، والصفحات الرئيسية والتقارير.

## حالة العمل

الرموز: `[ ]` لم يبدأ، `[-]` قيد التنفيذ، `[x]` مكتمل ومتحقق منه، `[!]` يحتاج قرارًا أو معالجة يدوية.

- [x] إعادة تصميم جدول المهام ومنع الروابط الطويلة من توسيع عمود المهمة وضغط باقي الجدول.
- [x] توحيد تحسينات الجداول العامة والالتفاف/القص الآمن للنصوص في صفحات القوائم والتقارير.

- [ ] فحص بصري على الموبايل وعلى نسخة السيرفر بعد الرفع.

### الصلاحيات والحسابات

- [x] منع المستخدم من منح دور يحتوي على صلاحيات لا يملكها.
- [x] فصل الدور الأساسي للمستخدم عن أدوار الفرق حتى لا يؤدي تعديل المستخدم إلى حذف صلاحيات فريقه.
- [x] إنهاء جلسة المستخدم المعطّل ومنع الجلسات القديمة من الاستمرار.
- [x] إبقاء صفحة الدخول متاحة حتى لو كان المتصفح يحمل جلسة/كوكي قديمة، بدل التحويل الإجباري إلى لوحة التحكم.
- [x] توجيه المستخدم بعد الدخول إلى صفحة يملك صلاحيتها، مع جعل الملف الشخصي وجهة آمنة إن لم يملك صلاحيات صفحات أخرى.
- [x] التعامل مع انتهاء CSRF/session أثناء ترك الصفحة مفتوحة: إنهاء الجلسة القديمة والعودة لصفحة الدخول برسالة واضحة بدل صفحة 419.
- [x] استبدال حذف المستخدم بتعطيله لحماية تاريخ الملكية والسجلات المرتبطة به.
- [x] تقييد قوائم العملاء والعروض والمشروعات والـ leads حسب نطاق صلاحيات المستخدم، مع تحقق مماثل في الخادم.
- [!] السجلات غير المسندة إلى مستخدم متاحة حاليًا لكل صاحب الصلاحية الأساسية. هذا جزء من آلية الاستلام الحالية، وتغييره يحتاج قرار business واضح.

### المبيعات والمدفوعات وعروض الأسعار

- [x] إصلاح endpoint تحويل عرض السعر إلى مبيعة؛ المسار موجود لكن الدالة غير موجودة.
- [x] منع إنشاء مبيعتين لنفس عرض السعر على مستوى التطبيق وقاعدة البيانات.
- [x] قفل سجل المبيعة داخل transaction عند تسجيل دفعة لمنع الدفع الزائد المتزامن.
- [x] تحويل حذف الدفعة إلى عملية Reversal موثقة مع soft delete للحفاظ على الأثر المالي.
- [x] منع حذف مبيعة لها دفعات، ومنع خفض إجماليها تحت القيمة المدفوعة أو إلغائها مع وجود دفعات.
- [x] رفض الدفعة الأولى الأكبر من الإجمالي بدل قصها تلقائيًا بصمت.
- [x] تحسين توليد رقم عرض السعر ليشمل السجلات المحذوفة soft delete ويمنع إعادة استخدام الرقم.
- [x] التحقق من تطابق أعداد عناصر الخدمة والكمية والسعر في الطلبات المعدّلة يدويًا.
- [x] إضافة سجل Reversal مستقل يوضح قيمة الدفعة وسبب عكسها ومن نفذه ووقته، مع عرضه في شاشة المبيعة.
- [!] Refund مالي فعلي (إرجاع مبلغ للعميل عبر وسيلة دفع) غير منفذ؛ يحتاج بيانات التحويل/الاسترداد وموافقات العمل، ولا ينبغي الخلط بينه وبين عكس قيد أُدخل بالخطأ.

### العملاء والـ Leads والمهام والمشروعات

## ملاحظات بيانات حالية من الفحص

- لا توجد دفعات زائدة حاليًا.
- لا توجد مبيعات مكررة لنفس عرض السعر حاليًا، لذلك يمكن إضافة unique index بأمان بعد فحص migration نفسه.
- لا توجد فروق حالية بين إجمالي عناصر المبيعات/العروض والإجمالي المسجل.
- لا توجد مبيعات ملغاة أو محذوفة مرتبطة بدفعات حاليًا.
- لا توجد مهام مفتوحة مسندة لأعضاء غير نشطين أو بدون أعضاء حسب الفحص الحالي.

## خطوات الرفع الآمن المقترحة

1. أخذ backup كامل لقاعدة البيانات و`storage/app`.
2. رفع الكود مع إبقاء ملف `.env` الخاص بالسيرفر كما هو.
3. التأكد من `APP_ENV=production` و`APP_DEBUG=false` و`APP_TIMEZONE=Africa/Cairo` وبيانات البريد والرابط الصحيح.
4. تفعيل وضع الصيانة لفترة قصيرة.
5. تشغيل `composer install --no-dev --optimize-autoloader` و`php artisan migrate --force`.
6. تشغيل `php artisan optimize:clear` ثم `php artisan optimize`.
7. إعادة تشغيل queue worker إن كان مستخدمًا، والتأكد من cron الخاص بـ scheduler.
8. إلغاء وضع الصيانة وتنفيذ smoke test للوظائف المالية والصلاحيات.

جلسات السيرفر: لا تغيّر `APP_KEY` عند الرفع؛ راجع `APP_URL` و`SESSION_DOMAIN` و`SESSION_SECURE_COOKIE` لتطابق نطاق HTTPS الفعلي، وتأكد من وجود جدول `sessions` وسلامة اتصال قاعدة البيانات. إذا كان هناك أكثر من سيرفر تطبيق، يجب أن تستخدم كلها نفس `APP_KEY` ومخزن جلسات مشترك. التعديل البرمجي يعالج مسارات التحويل وانتهاء الجلسة، لكنه لا يمكنه ضمان فتح الموقع أثناء توقف قاعدة البيانات أو وجود خطأ في إعدادات السيرفر.
