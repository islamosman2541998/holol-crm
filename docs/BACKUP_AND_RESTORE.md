# نسخ Holol CRM الاحتياطية واختبار الاسترجاع

## ما الذي يُحفظ؟

الأمر `php artisan backup:create` ينشئ ملف ZIP خاصًا يحتوي على نسخة قاعدة البيانات وكل ما داخل `storage/app`، بما في ذلك مرفقات المهام والمشروعات والملفات العامة. يحتوي الملف أيضًا على `manifest.json` وبصمة SHA-256 لكل عنصر. لا تُعلن النسخة جاهزة إلا بعد فحص جميع العناصر. عند الفشل يرجع الأمر exit code غير صفري ويسجل الخطأ في Laravel log.

لا يتضمن الأرشيف `.env` أو `APP_KEY`. احتفظ بنسخة آمنة منفصلة من إعدادات السيرفر والمفتاح؛ لا تغيّر `APP_KEY` عند الاسترجاع.

## تهيئة السيرفر

1. تأكد من وجود PHP `zip` وعميل `mysqldump` المناسب لقاعدة MySQL/MariaDB. الإعداد الافتراضي يبحث عن `mysqldump` في PATH. إذا لم يكن موجودًا، اضبط `BACKUP_MYSQLDUMP_BINARY` إلى مساره المطلق. لا تُمرر كلمة مرور قاعدة البيانات في سطر الأوامر؛ الأمر يستخدم إعدادات Laravel وبيئة العملية الفرعية.
2. المسار الافتراضي هو `storage/backups`، وهو خارج `public` وخارج `storage/app` حتى لا تنسخ النسخة نفسها. يمكن ضبط `BACKUP_PATH` إلى مسار خاص على قرص احتياطي موثوق ومشفّر. لا تضعه داخل مجلد الويب أو مجلد متزامن مكشوف. الملفات تحتوي على بيانات حساسة وغير مشفّرة داخل ZIP.
3. خذ نسخة ثانية خارج نفس السيرفر/القرص بوسيلة النسخ المؤسسية المتاحة لديك. هذا المشروع لا يملك حاليًا وجهة خارجية أو بيانات اعتماد لها؛ النسخة المحلية وحدها لا تحمي من فقدان السيرفر. لا توجد سياسة حذف تلقائي، لذلك راقب المساحة وحدد سياسة الاحتفاظ بعد تأمين النسخة الخارجية.
   قاعدة البيانات والملفات لا تُجمَّدان معًا في لحظة ذرية واحدة؛ شغّل النسخ في وقت نشاط منخفض. للنسخ المطلوبة قبل تغيير كبير، استخدم وضع الصيانة فترة قصيرة حتى لا يتغير مرفق أثناء النسخ.
4. تأكد أن Laravel scheduler يعمل كل دقيقة على السيرفر. إن لم يكن لديك cron قائم، أضف أمرًا واحدًا من نمط `* * * * * cd /absolute/project/path && /absolute/php/path artisan schedule:run` لدى مستخدم التطبيق. لا تضف cron مكررًا إن كان موجودًا. `php artisan schedule:list` يعرض المهمة: يوميًا 02:00 بتوقيت القاهرة.
5. بعد تغيير `.env` أو إعدادات cron، نفّذ `php artisan optimize:clear` ثم أعد تجهيز الكاش بالطريقة المعتادة عند النشر.

## اختبار النسخ والاسترجاع

```text
php artisan backup:create
php artisan backup:verify /absolute/path/to/holol-YYYYMMDD-HHMMSS-xxxxxxxx.zip
php artisan backup:restore-test /absolute/path/to/holol-YYYYMMDD-HHMMSS-xxxxxxxx.zip
```

`backup:restore-test` يفحص الأرشيف ثم يستخرج قاعدة البيانات إلى ملف مؤقت. في MySQL/MariaDB يُنشئ قاعدة مؤقتة باسم `holol_restore_test_...` ويستورد SQL ويفحص الجداول وسجلات migrations ثم يحذف **القاعدة المؤقتة فقط**. يحتاج المستخدم صلاحية `CREATE DATABASE` و`DROP DATABASE`، ووجود عميل `mysql` في PATH أو ضبط `BACKUP_MYSQL_BINARY`. نفّذه خارج وقت الذروة، ويُفضّل على بيئة اختبار/خادم منفصل. في SQLite يفحص سلامة قاعدة مستعادة مؤقتة. لا يستبدل هذا الأمر قاعدة التطبيق العاملة.

في حالة عطل حقيقي: لا تسترجع فوق قاعدة السيرفر مباشرة. أولًا خذ نسخة مما تبقى، ثم استرجع الأرشيف إلى بيئة اختبار منفصلة، وراجع وقت النسخة والبيانات والمرفقات، وبعد الموافقة نفّذ خطة نقل البيانات المناسبة. ملف ZIP يحفظ `storage/app` بنفس المسارات النسبية.

## التحقق المنفذ محليًا

- إنشاء أرشيف MySQL محلي والتحقق من جميع بصماته.
- استيراد SQL إلى قاعدة MySQL مؤقتة والتحقق من 37 جدولًا، ثم حذف قاعدة الاختبار المؤقتة.
- اختبار آلي يستعيد SQLite ومرفقًا تجريبيًا إلى مجلد معزول ويتحقق من البيانات، واختبار يكتشف تغيير محتوى الأرشيف.
- مجموعة الاختبارات الكاملة: 12 اختبارًا ناجحًا، 39 تأكيدًا.

هذا لا يثبت تشغيل cron أو وصول النسخ خارج السيرفر في بيئة الإنتاج؛ يجب فحصهما بعد الرفع.
